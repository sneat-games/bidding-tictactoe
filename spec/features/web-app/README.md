# Feature: Crazy Games Web App

**Status:** Implementing
**Source Ideas:** crazy-games-web-app

## Summary

Client-only Astro + TypeScript web build of Bidding Tic-Tac-Toe for CrazyGames, with vs-bot and WebRTC vs-friend modes, a PvP transport supplied by `@sneat/game-kit` against the shared Sneat Games signaling relay, and a vanilla TS port of `btttplay` as the engine; packaged as a static `dist/` zip plus full Play-with-Friends SDK v3 integration.

## Problem

The Bidding Tic-Tac-Toe engine exists only as Go server code (`server-go/btttplay`, `server-go/btttmatch`); there is no playable surface. CrazyGames distributes HTML5 games as self-contained static bundles with their SDK v3 and supports a Full Implementation Play-with-Friends multiplayer surface (account module, displayed usernames, room lifecycle, invite link, instant-multiplayer, round-based rematch) that is gated on a logged-in CrazyGames account. To ship on CrazyGames AND let a player challenge a CrazyGames friend — without spinning up a Sneat backend for the MVP — the game needs a browser-runnable engine, a UI that drives the SDK v3 multiplayer surface, and a signaling channel for WebRTC that is deliberately minimal (no DB, no auth, no game state) so it honors the founder's "no server side in MVP" intent in substance. The existing Go engine remains the rule-of-record so the parallel Sneat Competios cup can reuse the same game definition server-side.

## Behavior

The web app is a single Astro site that compiles to a static `dist/` bundle. The CrazyGames SDK v3 script is **injected on demand, and only on a CrazyGames surface** — a page served from a CrazyGames domain, a page framed by one, or a page explicitly opted in with `?cgsdk=1` for off-platform testing. Everywhere else the SDK has no job: it initialises to `environment: "disabled"` and does nothing, so fetching it is pure cost. A static third-party tag in the document head is also render-blocking, which is why one there delayed the menu on `bidding-tictactoe.sneat.games` by 7-10 seconds. When the SDK is loaded, `await window.CrazyGames.SDK.init()` still runs before any other SDK call; both the script load and `init()` are bounded by a timeout so a wedged third party can never hold the game on its loading screen. The environment (`local` on `localhost`/`127.0.0.1`, `crazygames` in production, `disabled` elsewhere) is checked before every SDK call, so the app degrades gracefully in preview tooling and on dev. On startup:

- If `game.inviteParams` is non-null, the app was launched from an invite link — route the player straight to the join flow with that `roomId`.
- Else if `game.isInstantMultiplayer === true`, the app was launched from the CrazyGames Multiplayer landing page — skip mode select and drop the player directly into a new private joinable room.
- Else show mode select (vs-bot / vs-friend).

In **vs-bot** mode the local TS port of `btttplay` resolves the turn against a TS bot strategy and renders the result (winner, taken cell, transferred bid, tie-break flag, board outcome). The bid auction is a first-price-**transfer**: the winner pays their bid to the loser (the loser's budget grows), so the total budget across both players is conserved across the whole match. After a win or a draw a rematch restarts in the same tab.

Every match screen uses one 2x2 layout in both modes: a **balances** card (top-left) over the **board** (bottom-left), and a **bid panel** card (top-right) over the **game log** (bottom-right). The left column is exactly the board's own width, so the balances card and the board are the same width; the right column is a single fixed width, so the bid panel and the game log are the same width. Below 720px the grid collapses to one column in the order balances, bid panel, board, log. Both players' balances are public: the balances card shows each side's remaining budget as a progress bar against the initial budget, so the numbers driving an auto-bid are always on screen before it fires.

A turn is **clocked**, and both deadlines are self-enforced — a client only ever auto-submits its OWN move, through the same commit-reveal path a manual move takes, so the two peers' boards cannot diverge on a timeout. Once one player's bid is in, the other has **10 seconds** to answer against a human, or **20 seconds** against the bot — nobody is kept waiting there, and the bot's bid is in from the first instant of every turn, so a 10-second window would put the human on a permanent sprint. Failing that their bid defaults to **0**, so the only real bid wins the turn and is transferred to the player who did not answer. If NEITHER player has bid **30 seconds** after the turn starts, each silent player's bid defaults to **50% of their own balance**, except that a player whose balance is strictly greater than their opponent's defaults to **opponent balance + 1** — the cheapest bid that cannot be outbid, and always affordable because a strictly greater balance is at least one more than the opponent's. The 10-second clock replaces the 30-second one as soon as either bid lands. An auto-submitted move takes the bot strategy's cell pick, so an away player still plays a sensible square. In vs-bot mode the bot commits its hidden bid at the start of the turn, so the human always plays against the 20-second clock and the 30-second stall case cannot arise. A **New game** control sits under the board for the whole vs-bot match so a player can start over without playing a lost position out; because it discards the position, both balances and the log, it arms on the first click and only restarts on a second. The clock is a session-layer rule: `resolveTurn` already discards the loser's cell, so neither `server-go/btttplay` nor its TS port changes to support it.

In **vs-friend** mode the whole PvP transport comes from `@sneat/game-kit`'s shared `pvp` module (`reserveRoomId`, `hostPeer`, `guestPeer`, `openTurnInbox`, `commitPayload`/`verifyPayload`); this game owns no signaling code of its own. The inviter reserves a `roomId` — a 6-character code from an unambiguous alphabet (no `0`/`O`/`1`/`I`), so it can be read aloud or copied without optical confusion — by calling `reserveRoomId({ gameId: "bidding-tictactoe" })`, which probes the relay until it gets a code no live room under that `gameId` already holds. It then calls `game.updateRoom({ roomId, isJoinable: true, inviteParams: { roomId } })`, generates `game.inviteLink({ roomId })`, displays the CrazyGames username (via `user.getUser`), and registers `game.addJoinRoomListener`. The invitee arrives via the share link (`#room=<code>`), via the Friends drawer (CrazyGames UI), via an invite link (`inviteParams.roomId`), or via the instant-multiplayer entry. Both peers then exchange SDP+ICE through the shared relay and open a WebRTC DataChannel. The host opens with `{kind: "hello", game, protocol, config}` and the guest answers `hello-ack` only once the game id, protocol version and match config all match, so a stale or mismatched client is a clean refusal rather than two peers silently playing different rules; the guest needs this because it joins straight off a link and has never seen a menu. The host always plays X and the guest O, derived from each peer's own role rather than sent over the wire.

Because Bidding Tic-Tac-Toe is a hidden-bid game, moves use the kit's commit-reveal protocol: each peer first sends `{kind: "commit", turn, hash, public}`, where `hash` is a SHA-256 commitment over the tuple `[bid, cell]` plus a fresh per-turn salt, and `public` carries the target cell in the clear — only the **bid** is hidden until reveal, and because the hash covers the cell too, a reveal cannot swap in a different cell than the one already committed publicly. Once both commits are in, both peers send `{kind: "reveal", turn, bid, salt}`; each verifies the opponent's reveal against the commitment hash it already holds and then locally runs `resolveTurn` on the revealed moves, so neither side can read the other's bid before commitment. A reveal that fails verification, or a revealed move the engine rejects as illegal, abandons the match rather than resolving a turn the two peers would score differently. After a win or draw, both peers can rematch in the same room without navigating back through the CrazyGames UI; `game.leftRoom()` fires only when a peer actually leaves. `settings.disableChat=true` disables chat (the MVP ships no chat UI; the settings listener is wired so a future chat surface honors it), `settings.muteAudio=true` mutes all game audio, and a settings change listener applies updates live.

The TS engine in `web/src/engine` is a faithful vanilla-TypeScript port of `server-go/btttplay` and mirrors its public surface: `Mark`, `Board`, `Outcome`, `Move`, `Game`, `TurnResult`, `newGame`, `resolveTurn`, `boardOutcome`, `emptyCells`, `parseBoard`, and the five error conditions. Test fixtures are ported from `btttplay_test.go` so any rule change in Go trips a TS test failure.

The signaling relay is **not deployed by this repo**. It is the shared Cloudflare Worker owned by `sneat-games/webrtc-relay` and deployed at `https://webrtc.sneat.games`, consumed here through `@sneat/game-kit` — one relay behind every Sneat Games title, so a signaling fix reaches all of them at once. Its routes are namespaced by `gameId` (`bidding-tictactoe` for this game) so two games' 6-character room codes can never collide: `POST /reserve/{gameId}/{roomId}` (reserve a code; `409` when taken, which is what makes `reserveRoomId` retry), `POST /signal/{gameId}/{roomId}/{host|guest}/{type}` to publish an offer/answer/ICE, `GET` on the same path to long-poll for what the other role published, and `DELETE /signal/{gameId}/{roomId}` to tear the room down. Entries live in a Workers KV namespace with a 5-minute TTL that is refreshed on every write. No auth, no DB, no game state traverses the relay; `gameId` and `roomId` are opaque capability segments it does not interpret. `@sneat/game-kit`'s `defaultRelayBase()` picks the production relay for every real origin — including a CrazyGames or itch.io iframe — and only falls back to `http://localhost:8787` on localhost/loopback; the kit's `test-relay.mjs` serves that local double in dev and e2e.

This game previously shipped its own single-purpose worker under `web/signaling-worker/`, deployed at `signal.bidding-tictactoe.sneat.games` with no `gameId` namespace. That directory and this game's private copies of the peer/room/turn-inbox code are gone: the duplication is what let a signaling fix land on one side and not the other. Retiring the old deployment itself is tracked separately from the code migration.

## Acceptance Criteria

- `web-app#ac:engine-port`: `web/src/engine` exports `Mark`, `Board`, `Outcome`, `Move`, `Game`, `TurnResult`, `newGame`, `resolveTurn`, `boardOutcome`, `emptyCells`, `parseBoard` with signatures and behaviour matching `server-go/btttplay`.
- `web-app#ac:engine-testsuite`: A TS test suite in `web/src/engine` reproduces every case in `btttplay_test.go` (Outcome, String/Parse round-trip, EmptyCells, ResolveTurn higher-bid/tie-break/errors/unchanged-on-error/game-over/budget-runs-out) and passes under the project's test runner.
- `web-app#ac:engine-budget-conservation`: `resolveTurn` transfers the winning bid to the loser (first-price-transfer); the sum of both players' budgets is invariant across all turns of a match. Both the Go engine and the TS port enforce this; tests in `btttplay_test.go` and `btttplay.test.ts` assert `budget[0] + budget[1] == 2 * initialBudget` after every resolved turn.
- `web-app#ac:bot-mode`: A human can complete a full vs-bot match in a browser: choose bid + cell, see turn result, reach a win or draw, and start a rematch without page reload.
- `web-app#ac:sdk-init`: When the SDK is loaded, `await window.CrazyGames.SDK.init()` runs before any other SDK call; the `environment` gate (`local`/`crazygames`/`disabled`) prevents SDK calls outside the supported environments so localhost and the preview tool both work without throwing. Both the script load and `init()` are bounded by a timeout, after which the app continues in degraded mode rather than staying on the loading screen.
- `web-app#ac:sdk-only-on-crazygames`: The CrazyGames SDK script is never fetched unless the page is a CrazyGames surface — served from a CrazyGames domain, framed by one, or opted in with `?cgsdk=1`. A direct visit to `bidding-tictactoe.sneat.games`, a local dev server, and a `file://` open of `dist/` all make zero requests to `sdk.crazygames.com`. Where the page is framed but the parent cannot be identified (no `ancestorOrigins` and a suppressed referrer), the check fails open and loads the SDK.
- `web-app#ac:vs-bot-restart`: The vs-bot screen carries a persistent New game control that starts a fresh match at any point, including mid-turn — it interrupts the turn in flight rather than waiting for the current move, and cancels the running clock so an abandoned turn cannot still auto-bid. It arms on first click and restarts only on a second, so a stray click cannot destroy a match in progress.
- `web-app#ac:home-link`: Clicking the "Bidding Tic-Tac-Toe" title returns to the mode-select menu from anywhere, fully resetting a match in progress (including any `#room=` fragment and live peer connection). Modified clicks (new tab/window) are left to the browser.
- `web-app#ac:match-over-banner`: The end-of-match banner states the result in the player's own terms with an emoji, colour and weight distinguishing win/loss/draw, then lists both final balances with their movement from the starting budget. Engine-level outcome names (`XWins`, `OWins`) never reach the player.
- `web-app#ac:byline`: The header credits Sneat.Games, linking to https://sneat.games/.
- `web-app#ac:instant-menu`: The mode-select menu replaces the boot placeholder without waiting on any third-party network request, so first interaction off CrazyGames does not depend on `sdk.crazygames.com` being reachable or fast.
- `web-app#ac:crazygames-friends`: A logged-in CrazyGames user sees their own username in-game; the inviter's room appears in the Friends drawer / invite link / instant-multiplayer entry; the invitee can join via any of these, and both peers' CrazyGames usernames are displayed in-game so friends can recognize each other.
- `web-app#ac:webrtc-signaling`: Two browser tabs (one inviter, one invitee via a share link or `inviteParams`) establish a WebRTC DataChannel through the shared relay using `@sneat/game-kit`'s `hostPeer`/`guestPeer`, exchange hidden moves with commit-reveal (`{kind:"commit", turn, hash, public}` before `{kind:"reveal", turn, bid, salt}`, both sides revealing only once both commits are in), and both boards agree on the final position with no other network round-trips.
- `web-app#ac:instant-multiplayer`: When `game.isInstantMultiplayer === true` at SDK init, the app skips mode select and drops the player directly into a new private joinable room.
- `web-app#ac:round-based-rematch`: After a win or draw, both peers can rematch in the same room without navigating back through the CrazyGames UI; `game.leftRoom()` fires only when a peer actually leaves.
- `web-app#ac:settings-compliance`: `settings.disableChat=true` disables chat (no chat UI ships; the listener is wired for future chat), `settings.muteAudio=true` mutes all game audio, and a settings change listener applies updates live.
- `web-app#ac:cf-worker-signaling`: PvP signaling is supplied by the shared `sneat-games/webrtc-relay` Cloudflare Worker at `https://webrtc.sneat.games`, consumed through `@sneat/game-kit`'s `pvp` module — this repo defines, deploys and vendors no signaling worker or peer/room code of its own. Every relay call is namespaced by `gameId: "bidding-tictactoe"`: room codes are reserved with `POST /reserve/{gameId}/{roomId}`, and SDP + ICE relay by `{gameId, roomId, role}` through a KV namespace with a 5-minute TTL. No DB, no auth, no game state. The dependency, the production domain and the local `test-relay.mjs` double are documented in `web/README.md`.
- `web-app#ac:static-dist`: `npm run build` produces a self-contained `dist/` that runs offline from the file system (no fetch required to start a vs-bot match) and is sized for Crazy Games submission.
- `web-app#ac:typecheck-and-lint`: `npm run typecheck` and `npm run lint` pass on the web workspace with zero errors.
- `web-app#ac:sneat-games-hosting`: This repo's only Cloudflare Worker (`web/host-worker/`) serves the static `dist/` build at `https://bidding-tictactoe.sneat.games/`, SPA-fallback so the `#room=<code>` share link works with no server route, no legacy Firebase `deploy.yml`.
- `web-app#ac:match-layout`: Both match screens render one 2x2 grid — balances card top-left, bid panel card top-right, board bottom-left, game log bottom-right. The left column equals the board's own width (so balances card width == board width) and the right column is a single fixed width (so bid panel width == game log width). Below 720px the grid collapses to a single column ordered balances, bid panel, board, log. The budget bars live in the balances card, not in the game log.
- `web-app#ac:late-bid-default`: Once one player's bid is in, the other has 10 seconds to submit against a human and 20 seconds against the bot. On expiry that player's own client auto-submits `bid: 0` through the normal move path, so the player who did bid wins the turn and transfers their bid to the player who did not. The countdown and the pending auto-bid are visible in the bid panel before it fires. This applies in both vs-bot (where the bot's hidden bid is committed at turn start) and vs-friend.
- `web-app#ac:stall-bid-default`: If neither player has bid 30 seconds after the turn starts, each silent player's client auto-submits `floor(ownBalance / 2)`, or `opponentBalance + 1` when `ownBalance > opponentBalance`. Both inputs are the balances already displayed in the balances card, and `opponentBalance + 1 <= ownBalance` holds whenever the rule applies, so the default bid is always affordable. The 10-second clock replaces the 30-second one as soon as either bid lands.
- `web-app#ac:timeout-no-divergence`: A timeout never resolves a turn on the opponent's behalf — each client auto-submits only its own move over the same commit-reveal path, so both peers resolve the identical pair of moves. When a peer stops responding entirely, the waiting player is shown a non-resolving "opponent is not responding" notice with a Leave control rather than a defaulted turn.
- `web-app#ac:share-link-invitation`: An inviter can copy a share link `https://bidding-tictactoe.sneat.games/#room=<6-char-code>`; a friend opening that link is dropped directly into the same match as the guest via the shared `webrtc.sneat.games` relay — no CrazyGames account or Friends drawer required. On CrazyGames the same `roomId` is additionally pushed to `game.updateRoom` so the Friends drawer and invite link work in parallel.

## Open Questions

- **Resolved:** `roomId` is a short human-readable 6-character code, not a uuid v4 — the invite UX wins, and the collision risk that argued for a uuid is answered by the relay itself: `POST /reserve/{gameId}/{roomId}` returns `409` for a code already in use and `@sneat/game-kit`'s `reserveRoomId` retries with a fresh one, while `gameId` namespacing keeps the code space per-game.
- Does any HTML5-SDK v3 lifecycle requirement (script-tag load order, init-time environment gate, sitelock) conflict with Astro's static output for the SDK script tag in `index.html`?
- Should the bot strategy be deterministic given a seed (for future competitive modes) or is randomness fine for the web app?
